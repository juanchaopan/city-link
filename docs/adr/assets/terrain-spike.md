# 探针：地形方案是否可行（Q-012）

这是探针代码，只用来回答问题，永远不合并进正式代码。

## 要回答的问题

在 8×8 城市群里按随机顺序首次占用位置时，服务端能否生成山丘、河流、湖泊、森林、海岸和矿产，让相邻城市完全接上，并满足 REQ-033 的保底规则？高度取 3 层还是 4 层？八方向道路、桥和坡道需要多少 2.5D 素材？

## 判据

| 编号 | 判据 | 通过条件 |
|---|---|---|
| C1 | 边界连续 | 共享边界高度全部相同，河流全部接上，相邻顶点高度差不超过 1 |
| C2 | 硬失败 | 整个城市群按随机顺序填满时，无法生成合格地形的次数为 0 |
| C3 | 保底 | 每座城市的可建面积不低于 45%（森林可清除，计入可建） |
| C4 | 首笔贸易 | 每座有内部相邻位置的城市，至少一个连接点不修桥就能从中心修通 |
| C5 | 全部连通 | 全部连接点在允许修桥后都能修通 |
| C6 | 耗时 | 64×64 单次生成 P95 不超过 100 毫秒（Node 单线程） |
| C7 | 素材 | 三种线路和八方向的坡道、桥素材不超过 150 张，并给出用量依据 |

用户没有参与判据的制定：这次探针由一次性工作进程执行，数值是工作进程按需求和成本约束自行设定的，由用户在拍板时确认或调整。

## 时间盒

最多三轮尝试。三轮后仍未满足判据，结论就是这条路成本过高。

## 环境

AMD Ryzen 9 7940HS，Windows 11，Node v24.22.1，单线程。样本是 8×8 城市群按随机顺序逐个占满，生成耗时包含保底检查和道路搜索。

## 三轮结果

| 轮次 | 改动 | 硬失败 | 发现 |
|---|---|---|---|
| 1 | 第一版算法 | 192 座中 27 座 | 海岸带被当成河流入口；山边界和海岸带在群角冲突 |
| 2 | 修复以上两点，水体和矿产调到可用比例 | 1920 座中 2 座 | 河流围住中心平地；森林有直线接缝，河流贴边 |
| 3 | 高度、森林和河流走向用全群噪声；河流避开边界；连续失败后河流改为汇入湖泊 | 6528 座中 0 座 | 判据全部满足，河流外观仍偏生硬 |

## 素材估算

这是按运行时分层拼接推算的数量，没有实际制作和渲染。全部斜坡高差都是 1 层，所以素材数量和总层数无关；层数只影响地表种类。

| 项目 | 算法 | 数量 |
|---|---|---|
| 地块形状 | 15 种形状 × 地表 | 3 层 2 种地表 30，4 层 3 种地表 45 |
| 水岸和海岸 | 各 16 张 | 32 |
| 森林、矿产叠加层 | 3 + 2 | 5 |
| 每种线路的平地 | 8 条支臂 + 1 个中心 | 9 |
| 每种线路的坡道 | 4 向直坡道 | 4 |
| 每种线路的桥 | 2 个正交方向 × 3 段 | 6 |
| 三种线路合计 | 19 × 3 | 57 |
| 地铁示意叠加层 | 8 条支臂 + 1 个中心 | 9 |
| **总计** | | **3 层 133，4 层 148** |

保留斜向坡道每种线路多 8 张，加上斜向桥再多 6 张，3 层总量到 175，超出判据。`assets.js` 验证了最省规则可行：64×64 下 1920 座城市（3 层、4 层各 960 座），平地八方向、坡上只走四向直坡道、桥只走正交方向，全部连接点都能修通。

鞍形地块（5、10）全程只占地块的 0.008% 左右，线路不能通过。

## 判断

| 判据 | 结果 |
|---|---|
| C1 边界连续 | 通过，0 违规 |
| C2 硬失败 | 通过，第三轮 6528 座 + `assets.js` 1920 座均为 0 |
| C3 保底 | 通过，最小 66.0% |
| C4、C5 道路 | 通过，含最省规则 |
| C6 耗时 | 通过，64×64 P95 约 26 毫秒 |
| C7 素材 | 按估算通过，需要去掉斜向坡道和斜向桥 |

建议采用：64×64、4 层高度、角点平台、全群噪声、线路只用直坡道和正交桥，可建面积保底可以从 45% 提到 60%。

## 还没验证的事

- 回归城市带着原地形落到新位置的情况没有测试。
- 河流外观仍偏生硬，有回环和长直段，湖泊偏小、偏圆，正式实现要继续打磨。
- 耗时来自高性能笔记本的 Node，不代表微信云开发。
- 素材量没有经过实际制作，建筑素材不在内。
- 同一城市群按顺序生成的并发控制只按串行模拟，没有实现锁。
