# ADR-0005 服务端使用微信云开发云函数

- 状态：提议
- 日期：2026-10-30
- 相关需求：REQ-014、REQ-019、REQ-021、REQ-024、REQ-027、REQ-033

## 背景

多人贸易需要服务端，成本要接近 0，运维要全自动。官方页面显示新用户可以免费体验一个环境六个月，基础套餐约 19.9 元/月，超额按量付费。配额页写单函数并发 20、数据库 QPS 30、连接数 20，计费页又写基础套餐 QPS 500，两者不一致。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 云开发云函数 | 成本最低，自带微信身份，几乎没有运维，有定时触发器和事务 | 配额不明，文档型数据库，绑定微信 | 尽量零成本 |
| 云托管容器 | 可以用 Fastify，常驻进程，迁移容易 | 按资源计费，数据库单独准备 | 需要常驻连接 |
| 自建云主机 | 技术最自由，可用 PostgreSQL | 固定月费，要管备份、安全和备案 | 有运维时间 |

## 决策

用户选择云开发云函数和云数据库。`game` 函数同时处理客户端请求和一个每分钟的定时触发器，用 `action` 路由。数据访问走 repository 接口，有云开发和内存两套实现。服务端不用 Web 框架，校验使用 zod，测试使用 Vitest，架构检查使用 dependency-cruiser。

这项决策要等 Q-008 探针通过后才接受。探针判据：
- 用模拟流量测出基础套餐实际的 QPS、并发和超时。
- 模拟 1 万日活的结算和同步，一个月费用不超过 Q-009 的上限。
- 结算单的提交和逐城入账在中断时能恢复。
- 地形生成含冷启动 P95 不超过 2 秒。

探针失败时，先延长同步间隔和结算周期；仍不够时改用云托管，repository 接口保持不变。

## 证据

无实测。按 1 万日活推算：高峰约 1000 人在线，每 60 秒同步一次约 17 次调用/秒，每次约 3 个数据库操作，合计约 50 QPS，已超过配额页的 30。

## 后果

- 好处：几乎不用运维，上线初期接近零成本，身份和分享自然打通。
- 代价：绑定微信平台；本地没有官方模拟环境，所以要靠内存后端和真实环境验证两层保证；每分钟定时任务每月约 4.3 万次调用，没有玩家时也在跑，所以活跃城市群为零时要尽快退出。
- 什么时候应该重新考虑：Q-008 不达标，或免费体验到期后成本超过上限。
