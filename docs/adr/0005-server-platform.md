# ADR-0005 服务端使用微信云开发云函数

- 状态：提议
- 日期：2026-10-31
- 修改日期：2026-11-14
- 相关需求：REQ-014、REQ-019、REQ-020、REQ-021、REQ-022、REQ-024、REQ-027、REQ-033、REQ-044；设计稿 `docs/design/data-model.md` 第 1、9、14 到 16 节，`server-impl.md`

## 背景

多人货运需要服务端，维护者只有一人。服务器不持续模拟城市：城市在手机上模拟，服务端只校验、写入账记录、按地区算城市之间的货运和外地客人、按国家汇总全国需求，再处理接口期限、开地区、城市结束这类后台任务。

现行文档写个人版环境 QPS 500、函数超时最大 900 秒。开发阶段可以使用免费的个人版，含 40,000 资源点/月；付费个人版约 19.9 元/月，额度相同。免费环境在小程序发布后第 15 天到期，到期后进入隔离期，不转付费就会被销毁。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 云开发云函数 | 自带微信身份，几乎没有运维，有定时触发器、事务和云存储 | 按调用计费，文档型数据库，绑定微信 | 上线初期规模小 |
| 云托管容器 | 可以用 Fastify，常驻进程，迁移容易 | 按资源计费，数据库单独准备 | 需要常驻连接 |
| 自建云主机 | 技术最自由，可用 PostgreSQL | 固定月费，要管备份、安全和备案 | 有运维时间 |

## 决策

用户选择云开发云函数、云数据库和云存储。

- **一个函数**：`game` 函数用 `action` 路由，同时处理客户端请求、定时触发、激励广告回调（`adCallback`，经 HTTP 访问服务对外，1 秒内回包）和机器人的管理通道（HMAC 签名）。超时设 60 秒；部署后要在控制台把超时调大，默认 3 秒，部署命令不会改它。运营开关和配置在函数实例里缓存 60 秒。
- **一个每分钟的定时触发器**：`tick` 按顺序做下面几件事，做满约 40 秒就停，没做完的下一分钟接着做（`server-impl.md` 第 7 节）：
  1. 按 border_pair.next_due_at 处理接口期限的开始、冻结到期和到期判定，不发通知；
  2. 按 region.next_settle_at 做地区结算；
  3. 国家汇总；
  4. 已确认超过 2 分钟还没执行的激励广告；
  5. job_queue 里的分段任务：开地区、城市入住、城市结束、注销、每日维护；
  6. 每小时第 0 分钟跑通知任务，发微信服务通知；每天 04:00 建当天的维护任务。
- **地区结算不走任务队列**：tick 查 next_settle_at 已到的地区，先以“next_settle_at 还是读到的值”为条件把它加一个结算周期（运营配置，默认一个游戏日），这一步就是租约，抢不到就跳过。各地区的 settle_offset 让结算时刻错开。触发间隔变长时 next_settle_at 照样工作，只是晚一点。
- **分段任务**：开地区、城市入住、城市结束、注销和每日维护都是 job_queue 里的接力任务，每段在限时内跑完，把游标写进 payload，lease_until 和 owner 防止两次触发同时跑一段，重试超过次数就告警。
- **数据保留期**，由每日维护任务清理（`data-model.md` 第 8、14 节）：
  - 玩家 30 天没打开游戏，正在经营的城市结束；
  - 玩家 180 天没上线，他的历史城市（city 记录和参观快照）删掉；玩家也可以随时永久删除历史城市；
  - 已计入超过 7 天的入账记录删掉；
  - 地区结算结果保留最近 3 天；
  - 站内信已读、已解决的 30 天后删，待处理和未领取的不删；
  - 过期的留位和位置预览记录删掉；
  - 注销按 `data-model.md` 第 8 节的步骤删掉这个玩家的全部数据，不设撤回期。
- **代码**：数据访问走 repository 接口，有云开发和内存两套实现。服务端不用 Web 框架，校验使用 zod，测试使用 Vitest，架构检查使用 dependency-cruiser。

环境 ID 是 `cloud1-d4g50k8p5a564b091`，开发阶段使用免费个人版，超限按量付费关闭。

这项决策要等 #25 实测后才接受。还没验证的判据：

- 定时触发器能不能每分钟（7 位 cron）、时区是不是北京时间。
- `game` 函数超时能不能设 60 秒、内存多少；冷启动加 256 格的一次同步能不能在 1 到 2 秒（256 MB 内存）。
- 请求包上限（决定离线回来时分批的大小）；一个事务最多几步（开新城一个事务写 7 份文档）；单文档多大、一次查询最多几条。
- 云存储的下载流量（已核数据、地形文件）是否计费、CDN 怎么算。
- 个人主体能不能给出激励广告回调的地址，是否要 HTTPS 和备案；冷启动能不能 1 秒内回包。
- 资源点的实际折算：查询和未命中的条件更新各算几次调用，统计可能延迟 2 天。
- 费用和 `data-model.md` 第 15 节的分项成本表一致。
- 更高并发：100 以上没有测完；个人版有没有数据回档。

失败时的退路：

- 定时触发做不到每分钟时，按实际的最小间隔跑，期限和结算照样工作，只是晚一点。
- 费用超出时先调运营开关里的同步间隔和结算周期；仍不够时改用云托管，repository 接口保持不变。
- 广告回调做不到时，按 `data-model.md` 第 10 节的退路，以手机报的“看完了”发奖励并按天限次。

## 证据

真实环境探测，2026-10-31，从开发者工具模拟器调用云函数：

| 判据 | 结果 |
|---|---|
| 单文档条件更新原子性 | 20 个并发更新，`final` 和 `updated` 都是 5，符合预期 |
| 相同 `_id` 并发写入 | 10 个并发只成功 1 个，符合预期 |
| 数据库读 | P50 27 毫秒，P95 53 毫秒，最大 67 毫秒 |
| 数据库写 | P50 36 毫秒，P95 59 毫秒，最大 63 毫秒 |
| 排序查询 | P50 29 毫秒，P95 38 毫秒，最大 45 毫秒 |
| 冷启动 | 首次调用 937 毫秒 |
| 64 格地形生成（热启动，早期算法） | 函数内 133 到 371 毫秒，客户端往返 724 到 934 毫秒 |
| 并发调用 | 10、20、50、100 全部成功；100 个用时 35.2 秒，主要受模拟器客户端限制，不等于服务端上限 |

条件更新和相同 `_id` 只成功一次，正是位置占用、接口占位（border_pair 的 version）、入账防重（credit 的 `_id`）和地区结算租约要用的语义。地形生成那一行用的是 64 格、不含河网的早期算法；256 格的地形在开地区任务里后台生成，不在玩家的请求里做，耗时由 #23 量。

费用：按设计稿的分项估算（`data-model.md` 第 15 节），1000 日活、每 2 分钟同步一次，约 145 到 155 元/月，100 元约撑 650 日活；内测约 60 座机器人城市每 30 分钟同步一次，约 15 到 20 元/月，在个人版套餐内。这些数都要按 256 格在 #25 里重测，内测一个月后按实际用量对照分项重算。2026-10-31 按 64 格和早期的结算方式做的费用模拟只作历史参考，原始假设见 `docs/adr/assets/cloudbase-summary.json`。

## 后果

- 好处：几乎不用运维，身份、分享、订阅消息和广告回调自然打通；位置、接口、入账和结算租约依赖的条件更新和唯一写入已经验证；数据库延迟足够低；地区结算和后台任务都挂在一个每分钟的触发器上，不需要常驻进程。
- 代价：绑定微信平台；费用随日活和同步频率线性增长，按估算约 650 日活就到 100 元/月；发布前要转付费环境；本地没有官方模拟环境，所以要靠内存后端和真实环境验证两层保证；个人版有没有数据回档仍未确认。
- 什么时候应该重新考虑：#25 实测的平台限制做不到上面的判据，资源点实测远高于估算，或费用超过 REQ-027 的上限。
