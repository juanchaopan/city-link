# ADR-0006 每城账本和结算单

- 状态：已接受
- 日期：2026-10-30
- 相关需求：REQ-013、REQ-014、REQ-015、REQ-019、REQ-021、REQ-036、REQ-037、REQ-038

## 背景

贸易自动运行，买方资金和卖方库存相互影响，货款和过路费要同时影响多座城市。在线玩家要即时到账，离线城市要定时记账。按 1 万日活推算，每条贸易连接一个事务时，每月约 5400 万次数据库操作；按城市汇总时，60 分钟一轮约 700 万次。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 每城一份账本，结算单加逐城入账 | 写入最少；中断后可重跑；不用区分同群和跨群 | 入账有几秒到一分钟的不一致 | 成本优先 |
| 每城一份账本，每条连接一个事务 | 双方和途经城市同时变化 | 调用量最高，配额风险大 | 流量小 |
| 每个城市群一份账本 | 群内一次写入 | 同群玩家抢写一份文档，跨群要特殊处理 | 结算极频繁 |
| 另配关系型数据库 | 事务和查询最强 | 多一项固定开支 | 预算充足 |

## 决策

- 账本按城市存储，航线和海运都只是两座城市之间的线路，没有群内和跨群的结算区别。
- 结算时先按城市汇总全部贸易和过路费，写入一份结算单作为提交点，再用条件更新逐城入账。每座城市记录已入账的结算单，所以重跑不会重复。
- 定时任务用每分钟触发的云函数，按城市群编号的哈希把每小时的工作分到 60 分钟，离线城市每小时记账一次。
- 玩家同步时立即结算自己城市的贸易，首笔贸易不用等待。
- 定时任务和在线结算用城市群租约排队，租约只用于防止同时结算，账本仍然属于城市。地形生成也使用这个租约。
- 同步使用批量操作日志：本地先生效，每 60 秒或退到后台时上传，服务端用 `libs/sim` 校验。配额紧张时服务端返回 `retryAfter`，客户端降低频率。
- 贸易、过路费和离线供货都按速率和时间差计算，中断后补算不会丢失收益。

## 证据

无实测，调用量按 1 万日活、150 个活跃城市群、每城 3 条贸易连接推算。

## 后果

- 好处：调用量最低，城市之间的结算规则统一，中断能自动恢复。
- 代价：结算单提交和入账之间有短暂不一致；同一城市群的在线结算可能因租约被占用而推迟到下次同步；需要结算单的保留和补做逻辑。
- 什么时候应该重新考虑：玩家能感知到不一致，或租约冲突频繁。
