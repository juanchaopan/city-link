# ADR-0001 地形生成和线路规则

- 状态：已接受
- 日期：2026-10-30
- 修改日期：2026-11-14
- 相关需求：REQ-003、REQ-013、REQ-033、REQ-034；设计稿 `docs/design/game-design.md` 第 2、4、15 节

## 背景

城市地图是 256×256 格（2026-11-03 定）。世界是国家 → 4×4 的地区 → 位置，开放一个地区时要为它的 16 个位置一次生成好地形：山丘、平地、河、湖、森林、海岸和矿，相邻位置的边界要完全接上。玩家取名之前地形就要就绪。

地形有真实高度，八方向线路在坡地和水面上的规则决定了 2.5D 素材量。服务端要按地形核对玩家的操作（矿产只长在有矿的格、修到边界的落点能不能接），手机和服务端看到的格子必须一模一样。

设计稿对每个位置的地形有这些硬要求：

- 有本气候 10 级专属奖励建筑需要的地形：寒冷要山，温和要湖，炎热要海或大湖；水边留出 6×6 的平地给紧挨水面的奖励建筑。
- 至少有一条能通航的河从城里穿过，这条能通航的河经河网连到本地区的其他城市和别的地区，水运沿途都能通航（河网见 ADR-0009）。
- 相邻两个位置的边界上，每条边都留出足够长的可建地段，接口只能落在这些地段上。
- 可建地在允许跨河架桥时连成一片，湖和陡坡不能把它隔断，每一段可建边都能修过去。
- 通航河的每一段每隔不超过若干格就有一处两岸平地、能架桥。
- 每种位置（沿海、口岸、内陆、河网汇合处）的家底差不多，各有长短。

## 候选方案

地形在哪里生成：

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 服务端开地区时生成，存成文件，手机下载 | 两端用同一份格子；可以走 CDN、按版本缓存 | 开地区要在后台分段跑；要占云存储 | 服务端要按地形核对 |
| 手机和服务端按种子各自生成 | 不用存文件 | 不同手机的浮点运算可能差出一格，服务端会误拒合法操作 | 地形只是背景 |

线路怎么过坡：

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 全部坡地和桥都走八方向，直坡用切坡路基 | 规划最自由，玩家不用记例外规则；路面水平，车是正的 | 素材最多，还要画挡墙和填方 | 优先保证规划感 |
| 全部坡地走八方向，路面贴坡 | 最容易画 | 车看起来是歪的 | 不在意细节 |
| 只有角形坡和桥走斜向 | 路面不侧倾 | 大部分坡是直坡，不能走斜线 | 想省素材 |
| 坡上和桥只走水平、垂直 | 素材最少 | 坡上和过河失去斜线 | 素材成本优先 |

## 决策

**地形只由服务端生成，手机下载。**

- 开放一个地区是 job_queue 里的分段任务：每段生成几个位置的地形文件，写 slot 上的小摘要（terrain_score、edge_buildable、mineral_area），16 个都好了才把地区设为开放。当前地区还剩 4 个空位时预生成下一个地区；当前国家只剩最后一个地区可开时，预生成下一个国家。表和任务见 `docs/design/data-model.md` 第 2 节。
- 地形文件每个位置一份，放在云存储，路径带国家、terrain_version 和位置；只有云函数能写。手机下载自己和邻居的，按版本缓存，不在手机上生成。服务端核对时读同一份。
- 国家的 seed 和 terrain_version 决定全国的地形；改生成算法时升 terrain_version，旧版本的文件保留。

**生成方法**（`docs/design/sim-impl.md` 第 1 节）：

1. 高度按全国坐标取噪声，用定点数算，相邻位置的纹理自然连续。
2. 用切比雪夫距离的约束传播把相邻格的高度差限制在一层以内；共享边界的角点用角点平台，避免两条边界在角上冲突。
3. 按 ADR-0009 的全国河网把河刻进地形，能通航的河按通航河宽刻。
4. 铺森林和矿。
5. 逐项验收背景里的硬要求；不过就换盐重试。
6. 算 terrain_score 和每条边的可接地段，写进地形文件和 slot 摘要。

**线路规则**：全部坡地和桥都走八方向。直坡上的 45° 斜路用切坡路基：路面保持水平，上下两侧用挡墙和填方接地形，路基用分层拼接绘制，样图见 `docs/adr/assets/q014-slope-road-samples.png`。转向只在平地发生，坡上和桥上保持方向；鞍形格线路不能通过；桥不挡船；湖和海不架桥。楼、设施、站、机场、奖励建筑和路口只放在同一高度的平地上。

**由 #23 地形探针定的参数**（`game-design.md` 第 15 节）：

| 参数 | 设计稿的要求 |
|---|---|
| 高度层数、一层坡占几格 | 由探针定 |
| 通航河宽 | 探针在 4 到 6 格里选 |
| 桥的最大跨度 | 不小于通航河最宽处加 2 格 |
| 能架桥的位置的最大间隔 | 由探针定，写进 Q-006 |
| 可建面积保底 | 由探针定 |
| 生成耗时 | 服务端一个位置不超过约 10 秒，一个地区在开地区任务里分段做完 |

探针结果写进本 ADR 的新版本。不达标时调参数；生成慢就再提前一个地区预生成。

下面“证据”里的 4 层、桥跨 5 格、可建面积保底 60% 和新手走廊都是 64 格时的结论，不直接用于 256 格。

## 证据

### 64 格探针（历史数据）

地形探针第三轮，64 格地图，3 层和 4 层各 1920 个位置，环境是 AMD Ryzen 9 7940HS 上的 Node v24.22.1：

| 指标 | 3 层 | 4 层 |
|---|---|---|
| 硬失败 | 0 | 0 |
| 边界、高度差、水位违规 | 0 | 0 |
| 可建面积 平均 / 最小 | 84.7% / 70.5% | 82.1% / 66.0% |
| 连接点可达失败（当时的判据） | 0 | 0 |
| 生成 P50 / P95 / 最大 | 20.7 / 26.3 / 130 毫秒 | 15.4 / 21.9 / 87 毫秒 |
| 每个位置存储 gzip 平均 | 550 字节 | 592 字节 |

全部 6528 个位置都没有硬失败；没有角点平台时，3 层和 4 层各有 19 个和 31 个失败。约束传播和角点平台在 256 格沿用。当时为了不修桥也能从市中心连到一个邻居，设了一条河流不能穿过的新手走廊；设计稿只要求可建地在允许架桥时连成一片，256 格是否还要新手走廊待定。

64 格时的线路素材估算：48 种坡地和轴线组合有 36 种需要路基；分层拼接用 40 张，逐形状整张绘制要 108 张。256 格的素材量在排期时按设计稿重新估算。

证据文件：`docs/adr/assets/terrain-spike.md`、`docs/adr/assets/terrain-results.json`、`docs/adr/assets/terrain-cluster-L4.png`、`docs/adr/assets/q014-slope-road-samples.png`。探针代码归档在标签 `archive/spike-terrain`。

### 256 格

还没有实测，由 #23 量。`sim-impl.md` 第 1 节的估算：256 格约是 64 格的 16 倍再加验收，服务端一个位置约 0.5 到 1.5 秒；地形文件压缩后每个位置约 20 到 40 KB；手机内存里自己一块约 128 KB，四个邻居降采样后各约 8 KB。

## 后果

- 好处：两端用同一份格子，服务端核对不会因为浮点差一格误拒；玩家取名前地形已就绪；城市地形连续且各不相同，在任何地形上都能用同样的八方向规则规划。
- 代价：开地区要在后台分段跑，要提前预生成；地形文件占云存储和下载流量（是否计费由 #25 核实）；线路和地块素材比最省方案多；切坡路基的最终美术还没有验证，样图只是几何示意。
- 什么时候应该重新考虑：#23 探针在 256 格上达不到背景里的硬要求或生成耗时；切坡路基的实际画面不可接受，此时退回角形坡方案，地形数据不用改；素材制作进度威胁到上线时间。
