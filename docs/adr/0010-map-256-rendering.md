# ADR-0010 256×256 地图的客户端渲染要求

- 状态：已接受（中端安卓真机帧率待验证）
- 日期：2026-11-04
- 相关需求：REQ-003、REQ-005、REQ-033；设计稿 `docs/design/game-design.md` 第 15 节“256 格满城渲染”

## 背景

地图定为 256×256 格（2026-11-03），面积是 128 格的 4 倍。目标是中端手机竖屏 30 帧（项目 CLAUDE.md）。ADR-0003 和 ADR-0004 已经定了按 16×16 分块、用 ParticleContainer 画地图，但当时按 64×64 验证，那时的证据不能直接用到 256 格。

美术探针 `spike/art-direction` 的画法是全城所有物体各一个精灵，只做了粗略的视野筛选，没有分块缓存。用它在同一台机器上量 128 和 256 两种城市，可以看出哪些开销跟着地图面积涨。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 分块绘制，只画视野里的分块；拉远时换成预画好的分块图 | 游戏视角的开销基本和地图面积无关；鸟瞰时每块只画一张图 | 分块图要在楼变化时重画，占显存；拉远时细节变少 | 地图大、物体多 |
| 全城每个物体一个精灵，按视野筛选 | 写法最简单，探针现在就是这样 | 每帧开销跟全城精灵数涨，256 格鸟瞰在桌面显卡上只有 48 帧 | 64 格以内的小地图 |
| 缩小地图或减少楼数 | 不用改画法 | 违背用户定的 256 格 | 前两种都达不到时的退路 |

## 决策

正式客户端照下面这些要求做，探针的画法不进正式代码：

1. **只画视野里的分块**。地图按 16×16 格分块（和交通小区同一套划分），每块一个容器，不在视野里的分块整块不画，地面也按块画，不整张铺。
2. **拉远时用预画的分块图**。缩放低于一个阈值时，每块换成一张预先画好的图，车和小装饰不画；分块里的楼变化时只重画那一块，分摊到多帧。阈值和分块图的分辨率在正式实现时量出来定。
3. **画面上的车最多约 100 辆**。车只是表现，模拟里的车流不受这个数影响（REQ-005）。
4. **图集每张不超过 4096×4096**。探针的图集是 4096×7935，超过很多手机的纹理上限；按主题拆成几张。
5. **按约 1 万栋楼验收**。设计稿的尺寸表目标是满城不超过约 1 万栋楼，性能验收按这个数做，不按探针生成器的物体数。

真机验收的判据：中端安卓竖屏，256 格满城、约 1 万栋楼，游戏视角和鸟瞰都不低于 30 帧，内存不超过微信小游戏的限制。达不到时依次：调低拉远阈值和分块图分辨率；降低画质档的默认值；最后缩小尺寸表让楼更少。

## 证据

美术探针 `spike/art-direction`，提交 4f0e42b（图集含 256 城用到的精灵）、a644642（规模试验加 256）、57838de（测量脚本 `spikes/art-direction/scripts/scale-fps.js`）。2026-11-03 测量，机器是 AMD Radeon 780M 核显、Chrome 无头模式、d3d11、关垂直同步，视口 390×844、dpr 3，每个场景量 5 秒。这是桌面核显，不代表手机。

帧率三个数依次是 P50、P95、最差，单位帧每秒。“视野内物体”是那一刻被挑出来画的楼、树和装饰数。

| 项目 | 128 格 | 256 格 |
|---|---|---|
| 全城精灵数 | 42,452 | 132,645 |
| 游戏视角（缩放 0.42），300 辆车 | 85 / 65 / 45，视野内物体 540 | 64 / 50 / 39，视野内物体 569 |
| 游戏视角，100 辆车 | 149 / 115 / 99 | 109 / 86 / 23（有一帧卡顿） |
| 半图缩小（缩放 0.078），不画车 | 179 / 109 / 78，视野内物体 3,029 | 103 / 66 / 34，视野内物体 5,798 |
| 默认视野，不画车 | 263 / 149 / 93，视野内物体 1,475 | 63 / 41 / 37，视野内物体 20,881 |
| 鸟瞰全图，不画车 | 345 / 156 / 105，视野内物体 1,961 | 48 / 38 / 33，视野内物体 25,720 |
| 垃圾回收后的 JS 堆 | 44 MB | 约 100 MB |
| 页面载入（含现场生成城市） | 40 秒 | 51 秒 |
| 存档（原始 / 压缩） | 111 / 17 KB | 192 / 22 KB |

原始数据：`docs/adr/assets/render-fps-128.json`、`docs/adr/assets/render-fps-256.json`。

从数据看：

- 游戏视角下两种地图视野内的物体差不多（540 和 569），256 格却从 85 帧降到 64 帧。这部分开销跟全城的精灵数涨，不跟屏幕上的东西涨。具体是哪一步（地面整片绘制、场景树遍历还是排序）没有单独量。
- 拉远以后 256 格视野内的物体是 128 格的 10 倍以上，帧率降得最多。逐个画精灵在鸟瞰时撑不住，要换成分块图。
- 载入时间是探针在页面里现场生成城市，正式游戏从存档载入，不现场生成；存档 22 KB，不是问题。

## 后果

- 好处：游戏视角的开销和地图面积基本无关，256 格和 128 格在手机上的帧率差距可以控制住；鸟瞰时每块只画一张图。
- 代价：分块图要占显存，楼变化时要重画对应的块；拉远时看不到车和小装饰；图集要拆成几张，素材脚本要跟着改。
- 什么时候应该重新考虑：中端安卓真机按上面的判据达不到 30 帧；或者分块图的显存超过微信小游戏的内存限制。
