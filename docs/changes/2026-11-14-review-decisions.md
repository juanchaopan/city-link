# 同步审查后定下的几条规则

- 日期：2026-11-14
- 级别：L2 需求变了（几条已有规则改写，没有新功能）；设计冲击 D0（游戏规则的业务代码还没有写）
- 来源：#21（PR #47）同步需求和架构时，本地代码审查找出设计稿没定或互相对不上的几处，用户逐条决定

## 变了什么

1. **水运经过别的地区**：同一地区两座城市之间的河段经过别的地区时，照常能水运；途经别的地区的城市按空白位置处理，不收过路费。水运过路费只在本地区收。
2. **同步先盖章再写别处**：服务端处理一次同步时，先以 sync_seq 为条件更新 city（盖章），成功以后才写离线记录、入账记录、边界接口、广告奖励的执行、城市结束任务和城市摘要；盖章失败的同步什么都不留下。
   - 盖章时 last_batch_result 只记新 sync_seq、调整量、要建的离线记录、要不要启动城市结束任务，和一个“盖章后的写入做完没有”的标记。函数在写完前中断时，下一次进入游戏或同步只补这两样（城市已经不在用就不补）；接口、过路费、广告的执行和城市摘要由那次同步按常规步骤重做：强制重判本城的接口、强制写城市摘要。
   - 过路费入账在一个事务里“入账记录不存在才写”，写成了才扣 toll_pending 并更新 toll_credited_at，重做时不会扣两次。
   - 修到边界在盖章后占不到接口时（对方同时修到），套用“服务端替你取消的工程”：标成已取消、全额冲减支出，响应带回“被对方抢先”，本城的 ports_version 加一让手机重读；手机下一次同步报已取消以后，服务端清掉这条记录。
   - running_port 和 border_pair 在盖章后的同一个事务里改。线头信的 _id 由 border_pair 编号、侧和 kind 推出，同一封信原地更新。sync_audit 只是统计，函数中断时少记一次。
3. **留存统计用微信后台**：次日留存、7 日留存和来源看微信小游戏后台自带的数据分析；“新玩家从进游戏到收到第一笔税用了多久”用微信自定义事件上报，只在玩家的第一座城报一次，时长从建城时刻算，“已上报”记在这座城的完整存档里；服务端不另存统计。内测在体验版里进行，自定义事件带上版本类型以便过滤；隐私指引里声明自定义事件上报。
4. **地铁要花建造费**：地铁站和地铁线要花建造费（价格见 Q-006）；公交站和公交线照旧免费造，只花维护费。地铁的建造界面沿用通用的价格气泡（`ui-map.md` 第 6 节），不另画效果图。
5. **不要新手走廊**：地形生成不要求从市中心到边界留一条不过河的平地。这是 64 格旧版的约束，旧版普通道路能修到邻居才用得上；现在普通道路只在本市，新手对外靠 2 级的内河码头。
6. 愿景里的三条假设（玩家愿意看视频不厌烦、按顺序填空位地区很快住满、7 天期限不逼走玩家）和“第一版不做隧道”保留。
7. 项目说明（CLAUDE.md、REVIEW.md）里“64 城的城市群”的旧说法改成国家、地区和 256×256 格城市的世界结构。

第 1、3、4、5、6 条由用户决定；第 2 条的方向由用户决定，下面的技术细节由协调会话按设计稿已有的做法定。

## 为什么

#21 把需求和架构按设计稿同步时，审查发现：河网是全国一棵树，同一地区两城之间的河可能绕到别的地区，设计稿没说怎么算；同步流程先写别处再盖章，撞车时会留下和城市记录对不上的接口状态和入账；REQ-028 要的留存数据没有数据设计；“站和线路免费造”写在公交和地铁共用的一节里，地铁也跟着免费；ADR-0001 留着 64 格时的新手走廊待定。这几处不定下来，实现时各写各的。
